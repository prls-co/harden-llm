# Issue 188 — preserve native responses on matching protocols

## 1. Decision and confidence

Use the accepted provider response as the basis for ordinary Chat and Responses output when the actual producing endpoint speaks the caller's protocol. Keep the normalized result for validation, retries, accounting, search evidence and translation. Qualify the gateway, published OpenAPI contract and Harden Go HTTP client together using fixtures in this repository.

| Question | Assessment | Evidence |
| --- | --- | --- |
| Do we know where the fields disappear? | Very high confidence | At `98a65f4`, the authenticated loopback witness returned 400 on explicit `reasoning.summary` with zero cache or provider operations. On an accepted request the Responses provider sent reasoning followed by a message. The caller received the message alone, with a generated ID. The matching Chat route dropped its native fingerprint and an unknown field. |
| Will carrying the accepted response fix ordinary JSON and cache replay? | High confidence in the design | The provider adapter already has the decoded response. The operation cache already serializes the accepted result and restores the producer's identity separately from the current execution. The missing information can cross these boundaries without adding an inference path. Release verification is recorded separately from this design assessment. |
| Does Harden’s current client schema accept the expanded output? | Confirmed incompatibility | At `98a65f4`, the existing `Response` schema accepted the one-message control. Adding either a reasoning item or an unknown top-level field made validation fail. The in-repo HTTP client uses this schema on successful responses. |

The local tests establish the contract failure. Production access records examined for the RCA contained status and route only. The frequency of affected production calls and the behavior of individual live upstream models remain unmeasured. ## 2. Alternatives

| Approach | What it delivers | When to choose it |
| --- | --- | --- |
| Accepted native response on matching ordinary routes | One public default. New provider fields and output item order survive without per-field modeling. | Recommended for the contract requested in #188. Qualify the existing and expanded shapes in Harden’s HTTP client tests. |
| Explicit opt-in to the native representation | Harden offers two response shapes and needs a selection rule, documentation and tests for both. | Consider only if Harden commits to preserving the old response shape as a separate public contract. |
| Add reasoning summaries to the current typed renderer | Smaller change for a client that needs only summaries. Still requires consumer compatibility work if applied by default. Each future item or field needs another mapping. | Choose only if the owner narrows #188. The unknown-field and arbitrary ordering requirements would remain open. |
| Forward upstream HTTP bodies or streams directly | Straightforward for unmodified, uncached responses. Recovery can reject that very response, and a second path would need its own cache, error, diagnostics and search behavior. | Unsuitable for the ordinary hardened endpoints. |

## 3. Public contract to establish

1. **Fidelity.** Preserve native IDs, timestamps, model, usage, extensions, member presence, nulls, integer precision and array order for an admitted success. Compare decoded JSON to the provider fixture. A replay of the same public representation must also retain the existing first-call body/stream equivalence with diagnostics off. JSON object member order and provider whitespace need no new guarantee.
2. **Compatibility fields.** Preserve native values where supplied. For a sparse response the gateway accepts today, fill the minimum fields its callers need using the existing projection rules and stable producer identity. In particular, supply `output_text` from accepted assistant text when absent. Qualify both an item-only native response and an `output_text`-only CPA fixture. Document what happens when a provider supplies conflicting text, or reports an actual model different from the requested alias. Preserve the distinction between the wire model and Harden's selected target. OpenAI describes aggregate `output_text` as an SDK convenience. [Harden client](../httpclient/responses.go) · [OpenAI response object]( https://developers.openai.com/api/reference/resources/responses/methods/create )
3. **Matching and admission.** Use the prepared wire endpoint and the successful attempt. Perplexity `/agent` shares the internal Responses protocol label and has a different wire contract. Admit ordinary `reasoning.summary` on an eligible Responses attempt and forward it beside `effort`. For an incompatible target, give the field-specific failure before model or search dispatch for that attempt. The ordinary Chat probability request guards, batch input restrictions and encrypted continuation input are separate contract decisions. [Provider request builder](../internal/providers/payload.go) · [Earlier encrypted continuation decision]( https://github.com/prls-co/harden-llm/issues/158 )
4. **Owned fields and data boundaries.** Reserve top-level `harden` for this request. Remove a provider collision before cache/storage and generate diagnostics on delivery only when requested. Preserve the existing search-source inclusion rules. Decide explicitly how an unsolicited `reasoning.encrypted_content` is handled before persisting arbitrary fields. The proposed first release supports visible summaries and omits that specific opaque field from the delivered and cached representation. Document this exception for review. Keep response bodies out of tracking, diagnostics and reference history for ordinary calls.
5. **Repair and search.** For an unmodified native success, retain item order. For a repaired result use the admitted producer's answer, model identity and usage, preserve observed search evidence from the generating attempt where applicable, and remove citation ranges that no longer match the returned text. For Jina, add only search evidence Harden actually produced, in the existing public location. Specify these edits in before/after fixtures, including echoed repair instructions or injected search context. Reconstruct the documented public fields for a transformed result if a native envelope cannot represent it faithfully. [Repair and replay regression](../internal/gateway/httpapi/web_search_projection_test.go) · [Citation decision](../docs/adr/ADR-HLLM-036-search-citation-evidence.md)

## 4. Work sequence and acceptance gates

### 4.1 Establish the failing contract and reader compatibility

- Extend `TEST-403` through the authenticated public handlers and a recording TLS upstream. Use known native response and message IDs, a summary, a function item interleaved with a message, and unknown top-level and nested fields. Include an integer above `2^53`, an explicit null and an omitted field. Use the pinned SDK for known items and a number-preserving JSON decoder for unknown members. Include the matching Chat equivalent.
- Test summary-only, effort-plus-summary, effort-only, and an accepted request where the provider returns reasoning unsolicited. Compare the outbound request and the first public response with independent fixtures. Track provider, search and cache counts.
- Add old and expanded wire fixtures to Harden’s OpenAPI and Go HTTP client tests. Accept native extensions while preserving structured-output validation. Cover a missing `output_text`, invalid structured content and a provider-reported model that differs from the requested alias. Verify that matching routes return the provider model and that requested diagnostics identify Harden’s selected target.
- **Acceptance requires a failing baseline.** The old gateway fails the native-field assertions. The revised in-repo client reads both supported shapes and continues to reject invalid structured output.

### 4.2 Carry the accepted response through the existing engine

- Capture a bounded JSON object and its actual wire format where the adapter already decodes successful upstream JSON, including the terminal `response.completed.response` object for upstream Responses SSE. Use one owned representation with number-preserving decoding. Retain normalized output for engine decisions.
- Make the native object available for ordinary rendering and its cache record only after the existing completion, refusal, accounting, schema and recovery checks succeed. Exercise both execution paths, including a rejected primary followed by a successful repair or rerun on another protocol. Persist only the winner and explicitly retained search evidence. Ensure eligible output has a usable final answer or supported tool handoff and that added choices/items cannot bypass admission.
- Compare uncached execution near the 16 MiB limit with today's path for bytes retained and allocations. Check the final encoded size after compatibility additions and diagnostics. Preserve the separate 64 KiB diagnostics bound and the pre-header failure for an oversized response.
- **Acceptance requires transport parity.** Accepted JSON and terminal upstream SSE yield equivalent native content. Rejected, incomplete and interrupted attempts cannot supply a success body. A successful cross-protocol recovery uses the translator.

### 4.3 Render JSON, preserve cache identity and isolate other callers

- At the ordinary HTTP boundary, select the native object for eligible successes and apply the documented edits once. Use the ordinary translator for cross-protocol calls. Batch uses both the existing renderer and the same OpenAPI response schema through `BatchItemResult.response`. Pin its current response fixture and schema boundary before widening the ordinary success contract. Also exercise direct Go and reference callers for incidental serialization of the native object. [Batch encoder](../internal/gateway/httpapi/jobs.go) · [OpenAPI contract](../api/openapi.yaml)
- Use the existing operation cache and PostgreSQL envelope. Distinguish entries that can reproduce native output from existing projection `v6` entries. Prefer a new projection identity for affected operations and natural expiry. Document the resulting cold misses on cached operations and keep old records readable by the previous gateway during rollback. If capture depends on caller mode, test two callers that prepare the same upstream operation in either order.
- Exercise `off`, `cache`, `refresh` and two API-key scopes. Compare fresh/hit public bodies with diagnostics off. With diagnostics on, verify stable producer identity and native usage, distinct execution IDs and accurate current accounting. A hit must invoke neither provider nor Jina. Confirm the real database round trip, including an escaped NUL and exact numeric representation, using the existing cache integration test. [Cache persistence](../stateful/cache.go) · [PostgreSQL test](../stateful/cache_draft_integration_test.go)
- **Acceptance requires fidelity on both deliveries.** The first call and the hit each satisfy the native fixture. A legacy entry cannot masquerade as a native hit. An unrelated batch or reference request still meets its own contract.

### 4.4 Implement final-only streams and publish the contract

- Continue buffering until the result is admitted. The current Responses stream writer assumes a fixed item shape and returns on an unfamiliar type. Preflight the event sequence before sending headers. Cover reasoning summaries, interleaved items, input with missing optional IDs, and a future item type. For a future type, retain the item in the terminal response even when there is no specialized delta event. Verify exact indices and one `response.completed`. Use the same final response as buffered JSON.
- For Chat, retain its chunk contract, tool-call deltas, opt-in usage and `[DONE]`. Carry native ID, creation time and applicable finish reason. Chat has no full-object terminal event. Explicitly document which native extensions are available in buffered JSON only, unless a tested chunk mapping exists. Check fresh and cached streams with the pinned SDK and raw events.
- Amend ADR-HLLM-032 and the ordinary success schemas, request schema and API guide. Verify package-copy parity and the durable batch schema separately. Run focused Go tests, `make test-fast`, and the real PostgreSQL gate via `make verify`. Use the repository's browser-free release gate for an authorized release.
- **Acceptance requires a complete stream.** Check event sequences, replay, error paths and SDK behavior against the published contract. Include a contract test against truncation when the stream's first item is reasoning.

### 4.5 Verify the Harden deliverables

1. Exercise the authenticated gateway and the repository’s HTTP client against the fixture matrix. Record the tested source, commands and results. Document the compatibility impact for readers that validate against the previous closed schema.
2. If a release is requested, qualify the dev gateway and record source and component identities. Rehearse rollback using the previous gateway and cache identity. Record any separately authorized live-provider check against its specific route and model.

The RCA witness, existing final-only stream, repair/replay and CPA transport regressions, and the current Harden schema were exercised during planning.
